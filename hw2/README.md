# CVSD HW2：RTL 設計與驗證報告

更新日期：2026-10-17（UTC+08:00）  
正式版驗證日期：2026-10-16

這份報告整理 HW2 圖形繪製 RTL（暫存器轉移層級硬體描述）的設計、最佳化過程與測試結果。正式版使用 **1 組光柵化工作單元（P=1），每組有 40 條像素測試通道（Q=40）**。四組公開測資全部通過，週期數為 **p1：4275，p2／p3／p4：各 96303**。兩套 lint（靜態 RTL 規則檢查）也都完整跑完，未豁免的 Fatal、Error 與 Warning 均為 0。官方成績與排名還沒公布。

## 1. 作業內容與開發方式

這次作業要先把頂點轉成螢幕座標，再透過三角形光柵化（判定三角形覆蓋哪些像素）找出要上色的位置，最後寫入 frame（輸出影像）。處理步驟如下：

1. 接收轉換矩陣、頂點與三角形索引資料。
2. 計算頂點的螢幕座標，把轉換結果與三角形索引存進 cache（內部資料暫存區）。
3. 將資料已經備齊的三角形交給工作單元，準備三條邊的 edge function（判定像素位於邊界哪一側的運算）與面積等資料。
4. 對要檢查的像素執行 coverage test（像素覆蓋測試），把結果記入 bitmap（每像素一個覆蓋位元的表）。
5. 透過 frame 介面，把已覆蓋的像素寫成指定顏色。

這次透過 Codex 修改 RTL、執行測試並修正問題。使用者用文字指令設定比較基準、選擇最佳化方案、要求跑完 lint，也決定恢復 payload reset（儲存資料本體的重設），以及最後要繳交哪些檔案。開發過程中有人參與判斷與監督。模型用量與執行時間整理在第 7 節，使用者實際投入的時間與費用則沒有完整紀錄。

## 2. 設計名詞、參數與正式版設定

### 2.1 Q 與 P：如何同時處理像素與三角形

**Q 與 P 是這份報告用來表示兩種平行處理方式的記號**，在 RTL 裡分別對應 `PIXEL_LANES` 與 `RASTER_GROUPS`。

- **Raster worker（光柵化工作單元）**：接收一個三角形，決定搜尋範圍，再分批測試像素、記錄覆蓋結果。一組 worker 同一時間處理一個三角形。
- **Pixel lane（像素測試通道）**：worker 裡的一條像素測試運算路徑，每輪 coverage 計算負責一個候選像素。
- **Q：每組 worker 的 lanes 數**。Q 越大，一般 coverage 處理時，同一個三角形每個時脈週期最多能測試的像素就越多。
- **P：worker 的組數**。P 越大，就能同時處理更多不同三角形的光柵化工作。

例如，Q=4、P=3 表示有 3 組 worker，每組 4 條 lanes，合計 12 條像素測試通道。正式版 Q=40、P=1 則有 1 組 worker、40 條 lanes。P×Q 就是整個設計的通道總數。每週期實際能測試多少像素，還要看資料是否備齊、包圍盒裡還剩多少像素，以及是否遇到需要特殊處理的數值。遇到這類數值時，正式版可能只啟用一條 lane。

Q、P 在建立 RTL 結構時就已決定，跑測試時不會自行改變。調大這兩個值會增加運算電路和連接資源，但總週期數未必會等比例減少。

**大寫 P 與小寫 p1～p4 意義不同**：P 是 worker 組數，p1、p2、p3、p4 是四組公開測資的名稱。

### 2.2 正式版設定

| 項目 | 設定與意義 |
|---|---|
| Q／`PIXEL_LANES` | 40，每組 worker 有 40 條像素測試通道 |
| P／`RASTER_GROUPS` | 1，使用 1 組光柵化工作單元 |
| `MAX_VERTICES` | 頂點資料的儲存空間為 65536 筆 |
| `MAX_TRIANGLES` | 三角形資料的儲存空間為 65536 筆 |
| Coverage 計算 | 保留完整 FP32（32-bit 單精度浮點數）edge 運算與原有 coverage 判斷 |
| Cache 資料 | 轉換後頂點座標共 64-bit；三角形三個索引各 16-bit，共 48-bit |
| Reset | 保留 payload 非同步 reset |
| 內部診斷 | 使用 `HW2_SIM_DIAGNOSTICS` 開關，需要時才加入診斷副本與探針 |
| 驗證工具 | Synopsys VCS T-2022.06、SpyGlass T-2022.06 |

開發過程曾測試 Q=64、P=1，最後採用的預設值是 Q=40、P=1。

`MAX_VERTICES`、`MAX_TRIANGLES` 決定預留多少儲存空間。每次測試實際使用的頂點與三角形數由輸入決定，不一定會用滿。

### 2.3 其他設計用語

| 名詞 | 本設計中的意思 |
|---|---|
| Viewport（繪製範圍） | 這次要繪製的矩形像素區域，寬、高由輸入決定；只搜尋這個範圍內的像素 |
| Frame／frame 介面 | 最後的輸出影像，以及讀寫影像記憶體的介面；frame 儲存每個像素的顏色 |
| Coverage test／edge function | 計算像素中心位於三角形三條邊的哪一側，再配合三角形方向判斷是否覆蓋，也會檢查浮點運算是否出錯 |
| Bbox／bounding box（包圍盒） | 包住三角形的矩形，矩形的邊與畫面水平、垂直方向平行；這次實作會再向外加上誤差裕量，縮小需要檢查的範圍 |
| Fallback（退回保守路徑） | 包圍盒無法通過數值檢查時，改掃描完整 viewport；最後是否覆蓋，仍由 coverage test 決定 |
| 緊密排程 | 把包圍盒內連續的候選像素交給 lanes；一列結束就接著處理下一列，減少排到範圍外位置的情況 |
| Cache／bank | Cache 是按照頂點或三角形編號讀寫的內部暫存區；bank 是其中一個分區，每個 cache bank 最多 256 筆。這裡沒有一般處理器 cache 的命中與資料替換機制 |
| Bitmap | 用 1 bit 記錄一個像素是否已被三角形覆蓋，並按列儲存；它只記錄覆蓋結果，frame 才儲存顏色 |
| Payload／非同步 reset | Payload 是 cache 裡的頂點座標、索引等資料；非同步 reset 表示 reset 生效時，不用等下一個時脈上升緣就會清除這些暫存資料 |
| `HW2_SIM_DIAGNOSTICS` | 編譯時加入額外診斷邏輯的開關，包括 scoreboard（追蹤資料是否備齊、工作是否派出或完成的檢查表）、內部探針與斷言 |
| Waiver（規則豁免） | 對有明確理由的特定 lint 訊息設定例外；報告中的問題數量會扣除這些已豁免訊息 |

## 3. 演算法與 RTL 最佳化

### 3.1 保守包圍盒

原本每個三角形都要檢查整個 viewport。改版後，先根據三個頂點的螢幕座標找出包圍盒，只檢查包圍盒與 viewport 重疊的區域。

浮點運算會有誤差，直接使用頂點圍出的矩形，可能漏掉原本 coverage test 會接受的邊界像素。因此，包圍盒會向外多留一些空間，作為 FP32 誤差裕量。如果座標、edge 或面積沒有通過數值檢查，或需要多留的空間太大，就改回搜尋完整 viewport。最後判斷像素是否覆蓋時，仍使用原有的 FP32 運算。

假設有 T 個三角形，viewport 大小為 W×H，第 t 個三角形加上誤差裕量、再限制於 viewport 內的搜尋面積為 A_t：

| 搜尋方式 | 需要做 coverage test 的像素數 |
|---|---|
| 完整 viewport | T×W×H |
| 包圍盒 | 各三角形 A_t 的總和 |

當三角形只佔畫面一小部分時，包圍盒能省下不少像素檢查。不過，最差情況仍是 O(T×W×H)。整個設計還需要時間讀入資料、準備三角形運算、分配工作和寫出 frame，所以少做多少次 coverage test，未必能直接換成相同比例的總週期減少。

### 3.2 緊密排程

把包圍盒內要測試的像素連續交給 lanes，一列結束就接著排下一列，讓 lanes 儘量用來處理範圍內的像素。搭配包圍盒後，Q=64 與正式版 Q=40 都維持了原先公開測資的目標週期數。

Q 從 65536 降到 40，表示像素測試通道變少了。晶片面積和功耗能減少多少，還需要綜合與實體設計的結果才能確認，目前尚未量測。

### 3.3 讓模擬與 lint 更容易處理

除了少測一些像素，也把原本較大的 RTL 資料結構與模組拆開：

| 調整 | 用意 |
|---|---|
| Cache 分 bank，另外拆出儲存模組 | 將讀寫邏輯分區，讓工具每次分析的結構較小 |
| 三角形索引縮為 16-bit | 配合 65536 筆頂點容量，減少儲存索引所需的位元數 |
| 分配三角形工作的邏輯分 bank | 把挑選下一個三角形、更新工作狀態的邏輯分區處理 |
| Bitmap 與 frame 邏輯按列拆開 | 每列使用 256-bit 介面，讓各模組處理較小的資料範圍 |
| 用開關控制診斷程式 | 需要診斷時才加入 cache 副本、scoreboard、探針與斷言 |
| 保留功能邏輯與 reset | Lint 仍檢查正式功能；payload reset 也依 enhanced lint 要求保留 |

修改時的目標是讓輸出結果與原有週期數保持一致。各次測試使用的版本、工具選項和伺服器負載不完全相同，因此還不能單憑執行時間，就認定某一項修改帶來多少倍加速。要比較這件事，需要在相同條件下重新測量。

## 4. 開發歷程與問題修復

| 階段 | 處理內容 | 結果與取捨 |
|---|---|---|
| 建立比較基準 | 使用 Q=65536、P=1 的版本 | 目前保留的基準紀錄包含 p1=4275 cycles |
| 包圍盒與緊密排程 | 改測 Q=64、P=1 | p1=4275，p2／p3／p4 各 96303 cycles，全部 PASS |
| 減少 lanes 數 | 正式版改用 Q=40、P=1 | 四組公開測資維持相同週期數 |
| 嘗試調整 cache 與 reset | 曾移除 payload reset，希望讓工具更容易處理 | Enhanced lint 不接受這種做法，因此恢復 reset，沒有為此新增 waiver |
| 處理 lint 跑太久的問題 | 拆開大型儲存、bitmap、工作分配與 frame 邏輯，每套設定 1800 秒上限 | 最後兩套完整 lint 都在上限內完成 |
| 修正 enhanced lint 警告 | 處理診斷程式、位元數、未使用輸入及工具設定問題 | 最後未豁免的 Fatal／Error／Warning 均為 0 |

以下正式版結果都是恢復 reset 後測得的。先前移除 reset 的嘗試只作為開發過程的紀錄。

### 5.3 三角形覆蓋與浮點異常測試

171 組 worker 測資包含 **43 組指定案例與 128 組隨機案例**。指定案例檢查不同畫面尺寸、零寬或零高的 viewport、順時針與逆時針三角形、畫面外的三角形、面積為零的三角形，以及接近共線、非常小或座標很大的情況。隨機案例會改變三角形的位置與大小，部分刻意讓三個頂點接近同一直線。

隨機部分使用固定 seed `20261013`。Seed 是亂數產生器的起始值，固定它可以重現相同的資料。預期的 bitmap 由另外撰寫的 Python／NumPy 程式，以 FP32 計算整個 viewport，再交給 VCS 與 RTL 逐像素比較。部分三角形還會重複送入，確認原本已覆蓋的像素不會消失。**171 組全部通過，沒有 bitmap 差異。**

另有 3 組案例專門檢查浮點 fault（運算異常回報）：

| 案例 | 要確認的行為 | 結果 |
|---|---|---|
| 先用一般三角形覆蓋 2×3 個像素 | 建立六個已覆蓋像素，供下一步使用 | PASS，六個像素皆保留 |
| 不清空 bitmap，再送入會讓部分 edge 乘法溢位的極端三角形 | 已覆蓋、原本應跳過的像素，不應額外觸發 fault | PASS，沒有多報 fault，bitmap 不變 |
| 清空 bitmap，重新送入同一個極端三角形 | 這次需要實際檢查像素，應正常偵測到 fault | PASS，有偵測到 fault |

### 5.4 包圍盒與 frame writer 測試

包圍盒另外做過 **5,000 個三角形的 FP32 模型檢查**，包含隨機、接近共線及大範圍座標。檢查方式是先找出完整 viewport 中會通過 coverage test 的像素，再確認縮小後的搜尋範圍沒有把這些像素排除。結果沒有發現漏點；其中 2,354 個三角形使用完整 viewport 的 fallback。這是包圍盒規則的模型檢查，與把 5,000 組資料送進完整 RTL 模擬是不同的測試。

Frame writer 是挑選下一個待寫像素、安排輸出順序的模組。修改時，曾自行產生 **3,000 個週期**的輸入，在每個時脈更新前後各比較一次，共 **6,000 個比對時點**。測試包含同時新增覆蓋像素與取出待寫像素、暫停輸出、重複覆蓋、較小位址的像素晚到，以及重新開始一張影像。亂數起始值固定為 `0x31415926`。

這項測試比較新舊 writer 是否選出相同位址、是否還有待寫像素，以及哪些像素已經安排寫出，結果 PASS。它驗證的是當時開發版與舊版的行為一致性。

### 5.5 Cache 單元測試

Cache 以 **65536 筆容量**建立，使用固定亂數起始值 `0x1ad23456` 產生資料，共做了 **6,210 項檢查，全部 PASS**。測試採指定位置與隨機抽查，沒有逐筆寫遍全部 65536 個位置。

| 測試項目 | 檢查方式 | 結果 |
|---|---|---|
| 邊界與隨機讀寫 | 共 1,030 次寫入，包含位址 0、255、256、32768、65534、65535，再搭配隨機位址 | PASS |
| 不同資料寬度 | 同時測試 64-bit 與 48-bit cache | PASS |
| 多個讀取埠 | 每次由 3 個讀取埠讀取，確認各自的資料 | PASS |
| Reset 後重新使用 | 重設後先停用讀取，再重寫最後一筆資料並讀回 | PASS |
| 停用讀取 | 讀取未啟用時應輸出 0，即使位址帶有 X（未知值）也一樣 | PASS |

6,210 是資料比對的次數，包含不同寬度與不同讀取埠的檢查，不是 6,210 組完整圖形測資。

### 5.6 完整 RTL 的逐週期比較

將修改前後的 RTL 放進模擬器，逐個週期比較行為，**13 組自行產生的案例全部 PASS**。這項測試使用 Q=4、P=3、16×16 viewport、頂點容量 128、三角形容量 1024。

| 案例編號 | 測試內容 | 結果 |
|---|---|---|
| 1 | 沒有頂點、沒有三角形的空工作 | PASS |
| 2 | 1 個頂點、15 組三角形索引，檢查頂點重複的退化情況 | PASS |
| 3 | 128 個頂點、120 個三角形，連續接收資料並安排工作 | PASS |
| 4 | 同樣使用 128 個頂點、120 個三角形，但讓 valid（資料有效訊號）暫時中斷，間隔參數設為 30 | PASS |
| 5 | 唯一的三角形引用最後 3 個頂點，確認會等資料備齊再處理 | PASS |
| 6、8、9 | 分別在三個索引位置放入 `0xffff0000`，確認錯誤索引沒有被截短後誤當成合法值 | 全部 PASS |
| 7 | 調整投影矩陣，讓頂點轉換遇到除數為零 | PASS，錯誤回報與舊版一致 |

除了最後的影像，也逐週期比較外部介面的位址、資料與控制訊號、送給各 worker 的三角形編號，以及浮點運算狀態。另外還會檢查矩陣尚未備齊時不提早轉換頂點、暫存的頂點資料不超過 16 筆，以及 frame 不會重複寫入同一個像素位置。

這些測試顯示，修改前後在已測範圍內的行為一致。不過，逐週期比較的對照是舊版 RTL，其他自製測試也只涵蓋指定或抽樣的輸入，因此還不能保證所有可能的輸入都符合規格。隱藏測資是否通過，仍要等官方結果。

### 6.1 正式版量測

兩套 lint 都完整跑完，每套最多等待 **1800 秒（30 分鐘）**。

RSS（Resident Set Size）是程序常駐的實體記憶體用量。表中列的是各次執行觀察到的單一程序最高用量，沒有把所有子程序加在一起。KiB 為 1024 bytes，GiB 為 1024³ bytes。耗時來自各一次正式版執行，還沒有用多次測量計算平均值。

### 6.2 規則豁免說明

測試環境會先把背景設成白色，RTL 只需要把已覆蓋的像素寫成藍色，因此沒有使用 frame 介面的 `rdataf`（frame 記憶體讀回資料）輸入。這個輸入是必要介面的一部分，所以保留原有的 W240 規則豁免。工具會把同一個輸入的明細和摘要分成兩條豁免訊息。上表的零 Warning，是扣除這些豁免後的結果。
